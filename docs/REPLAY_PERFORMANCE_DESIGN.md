# リプレイ検証ランタイム設計

## 目的

リプレイの正確性を落とさず、超高速再生でも MT5 のチャートと操作 UI を止めない。

## 実装済みの基本原則

- 検証の進行位置はソースティック配列を基準にする。`CustomTicksAdd` の戻り値は描画結果であり、検証済みティック数ではない。
- 1 回の `OnTimer` の最大処理数を `InpMaxTicksPerTimer`（既定 2,000）で制限する。超過分は次回へ持ち越し、ティックは破棄しない。
- 時間比率モードにおいてバッチ制限到達時は、仮想時計を実際に評価可能な終端ティック時刻へクランプする（Graceful Slowdown）。これにより、壁時計のみが先走って約定時刻と約定価格が逆転する因果律矛盾を完全に防止する。ティック枚数モードは未処理の小数・整数累積を保持する。
- デュアルフィード（Subシンボル）は Main シンボルが実際に配信した最新ティック時刻に厳密同期させ、かつ Sub 側にもバッチ制限を適用して時間軸スキューと UI フリーズを防止する。
- A-B ループは、仮想時計が B を飛び越えても B までのソースティックを先に検証してから A へ戻る。インデックス境界の未初期化による永久停止防止ガードを備える。
- チャート描画とステータス通知は検証ループから独立させる。UI は最新スナップショットをフレーム単位（`requestAnimationFrame`）で適用し、`ERROR` 通知などの離散イベントは間引かず即時反映する。
- IPC の連続した `SEEK` / `CONTROL` は、他のイベントをまたがない範囲で最新値へ集約する。

## チューニング指針

`InpMaxTicksPerTimer` は 64〜10,000 にクランプされる。通常は 2,000 を基準にし、低スペック端末では 500〜1,000、描画を最小化した検証では 5,000〜10,000 を目安にする。値を上げるほどスループットは上がるが、MT5 のチャートイベントの待ち時間も増える。

## 正確性の不変条件

1. 同じ入力ティック列・同じ設定・同じ注文列からは、バッチサイズに関係なく同じ約定履歴になる。
2. バックプレッシャー発生中も `m_current_idx` は評価済み範囲だけ進み、仮想時計 `m_virtual_current_msc` は評価済み最新ティック時刻と常に整合する。
3. シーク・一時停止・速度変更では時間累積器をリセットし、前の再生区間の端数を持ち越さない。また、一時停止時は仮想時計を表示ティック時刻に同期させる。

## 今後の計測項目

ティック処理数/秒、`m_current_idx` の遅延、`CustomTicksAdd` 時間、チャート再描画時間、IPC キュー長をステータスへ追加すると、端末ごとの最適値を自動選択できる。
